# 案例：AWW'26 公测夜（2026-09-24）

> 一次真实跑过的活动，用来检查这套模板在实战里长什么样。人名已隐去，保留可验证的过程和教训。
>
> 完整原始材料（含活动记录与证据）在飞书：[AI 全球化增长公测夜：活动记录与原始证据](https://my.feishu.cn/wiki/WIIuwmnTKiguO6kfhCyc7eARnXg)

## 背景

| 项 | 内容 |
| --- | --- |
| 形式 | 2 小时线下分享 + 现场测试 |
| 主题 | 从「WhatsApp 是什么」到第一批海外用户 |
| 场地 | 借一个开发者社群的场次（第 21 场） |
| 报名 | 社群报名 + 平台申请表 + 表单引流 |
| 主讲 | 1 人 |

## 设计：五段主线

```
认识人 → 测试系统 → 界定边界 → 提案合并 → 投票迭代
```

其中三个设计是这场活动的核心：

1. **按"你最想改进哪一层"站队分组** —— 代替按产品类型分组。好处是自我介绍里"我最卡的事"自然对齐所在组，后面的讨论靶子直接由分组决定。
2. **举牌判定（🤯 / ✅ / ❌）** —— 每次演示后全场举牌，❌ 当场进"待建清单"。
3. **现场合并仪式** —— 投票最高的提案当场并入系统，大屏显示 before / after。

## 实际发生了什么

诚实版本比设计版本有用。

| 计划 | 实际 |
| --- | --- |
| T-7 开始宣发 | **T-3 才写第一篇推文** |
| 提前彩排 | 没有彩排 |
| 准备 PPT | 现场**没有 PPT**，讲了一份准备做 PPT 用的 Markdown 文档 |
| 提前 1 小时到场 | **开场前 10 分钟**才到 |
| 开场就有人 | **前 20 分钟只有主讲、场地负责人和朋友** |
| 全程录音 | 有录音，但事后没有系统整理 |

转折点：开场 20 分钟后人陆续到了。真正聊起来之后，现场从"演讲"变成了"对话"。

## 起了作用的东西

- **小规模反而更有效**。人少时能逐个人了解具体问题，多轮次回应——比抽象准备很多内容更有价值。
- **会前问题池**。有人在申请表里认真填了需求，于是现场有了"明确可以回答问题的对象"，而不是猜观众想听什么。
- **站队分组**。省掉了现场二次组织，开场就有归属感。
- **陌生人变熟人**。有过线上互动但从未单独交流的人报了名，活动成了建立联系的契机。

## 没起作用的东西（这份模板因此做了修改）

| 问题 | 模板里的对应改动 |
| --- | --- |
| 宣发太晚，报名不足 | `checklist.md` 把宣发锁定在 **T-7**，并要求 T-3 核对报名数，低于 60% 加推一轮 |
| 没有彩排，开场垮 | `checklist.md` 增加 **T-1 彩排开场 5 分钟** |
| 没有 PPT | `templates/物料清单.md` 明确"预跑录屏 + 可播版本"，不依赖现场网络 |
| 开场 20 分钟无人到场 | `templates/议程手册.md` 增加"人数不足时合并成 2 组，环节不减"的弹性规则 |
| 没有记录到场人数 | `checklist.md` 散场后第一项就是"合并记录与投票数据入库" |
| 群内零预热 | `templates/宣发清单.md` 的 T-1 增加"活动群预热"动作 |

## 结果

- 活动结束后群内 44 人
- 拿到了真实反馈和几条可执行提案
- 暴露出一个更重要的判断：**这个阶段小规模对话比大型发布会更合适**

## 可以带走的结论

1. **别在宣发上省时间**。内容和场地都可以临时救，报名量救不回来。
2. **开场前 20 分钟必须有人**。要么安排提前到场的熟人，要么把开场设计成"人少也能进行"的形式（圆桌而不是演讲）。
3. **问题池是命门**。有人认真填了需求，现场才有得聊。
4. **小规模不是失败**。如果场地来了 30 人但每个人只说了 10 秒，不如 8 个人每人聊 10 分钟。
