## 分组逻辑（替代产品类型分组）

按"**你最想改进 OS 的哪一层**"站队：常识层组 / Deep Dive 层组 / Toolkit 层组 / 反馈与迭代层组。好处：①自我介绍里"我最卡的一件事"自然对齐所在层；②4b 的讨论靶子直接由分组决定，无需二次组织；③每组提案正好覆盖 OS 的一个模块，合并仪式的素材分布均匀。

## 两个风险的预防（写死在流程里）

1. **现场测试不冷启动**：问题池与测试任务从会前表单预收（已征集的卡点/主题就是题库），现场提问是插队加菜——保证前3问必有质量；AI 会话预加载知识库，每次应答≤90秒；**Skill 实测以预跑结果为主展示，观众实测只选最简单的 Prompt 类工具**，复杂 skill 一律演示成品
2. **现场 coding 不裸奔**：合并动作全部走**预置模板**——提案→OS 条目的合并格式提前做好，现场只是填内容+展示 before/after；代码级 coding 一个不做，复杂提案一律进 roadmap

## 举牌判定的话术铺垫（pitch 结尾用）

> "接下来你们的每一票，都在帮我判断这个系统离'有用'有多远。🤯 越多，说明 aha 时刻成立；❌ 越多，说明 v0.2 该往哪走——你们今晚不是体验者，是第一次正式的用户测试。"

## 角色边界（不变）

- 测试环节你是**演示者**，不辩护——❌ 了就记入待建，说"好，这条进 v0.2"
- 讨论环节你是**规则设计者**，走动只答工具/名词/入口三类问题
- 合并环节你是**执行者**——只 merge 投票结果，不夹带自己的偏好
